* uriparse

An RFC 3986 URI parser for Chez Scheme, in portable R6RS.

#+begin_quote
✨ *AI Disclosure:* LLMs are used extensively in the planning and development of this project.
#+end_quote

** What it does

- *Parses.* ~(uri collect)~ splits a URI reference into its five components —
  scheme, authority, path, query, fragment — in any of three modes (~uri~,
  ~relative-ref~, ~uri-reference~). Input may arrive in any number of chunks.
- *Validates.* ~uri-parse-validate~ checks every component's charset and the
  authority grammar: userinfo, host (reg-name, IPv4address, IP-literal →
  IPv6address / IPvFuture) and port. It accepts exactly the byte strings RFC 3986
  Appendix A accepts, per mode.
- *Resolves.* ~(uri path)~ (§5.2.3 merge, §5.2.4 remove-dot-segments),
  ~(uri resolve)~ (§5.2.2 transform-references) and ~(uri recompose)~ (§5.3) turn
  a base and a reference into a target URI. All 42 examples in RFC 3986 §5.4 pass.
- *Normalizes.* ~(uri normalize)~ applies §6.2.2 syntax-based normalization:
  scheme and host case, uppercase percent-encoding hex, and decoding of
  unreserved characters. ~(uri percent)~ decodes and encodes.
- *Parses CONNECT targets.* ~uri-parse-authority-form~ parses an RFC 9112
  authority-form ~host:port~.
- *Fits a server.* ~uri-collector-reset!~ reuses a collector without
  reallocating. ~uri-parse-result-validate~ validates a result you already have.
  ~validate-component~ and ~validate-authority~ check a ~[start, end)~ range of
  your own buffer in place, copying nothing.

** Scope and limits

- ~uri-parse~ is a lenient splitter by design: it accepts bytes the ABNF
  rejects. Strict checking is the separate ~uri-parse-validate~ pass.
- The validation claim is accept/reject equivalence with Appendix A, per mode.
  It is checked by an exhaustive sweep of short inputs (length 5, a 12-byte
  alphabet), the RFC's own vectors, and an adversarial corpus. Error codes and
  offsets are tested separately, not covered by that claim.
- ~(uri normalize)~ does not remove dot-segments. That is reference
  resolution's job (§5.2.4) and lives in ~(uri resolve)~. To get a normalized
  target, normalize before resolving: decoding ~%2E~ to ~.~ creates dot-segments
  that resolution then removes.
- Resolution is strict (§5.2.2 with strict = true): ~http:g~ against
  ~http://a/b/c/d;p?q~ is ~http:g~, not the RFC 1630 compatible
  ~http://a/b/c/g~.
- Recomposition round-trips every parse result, but not every hand-built
  component set. A scheme-less relative path whose first segment contains ~:~
  recomposes to a scheme, and a no-authority path beginning ~//~ recomposes to an
  authority. §5.3 omits §4.2's disambiguating ~./~ on purpose.
- Portability: the source is R6RS and imports only ~(rnrs)~,
  ~(byte-machine ...)~ and its own libraries, and a test checks this. Only Chez
  Scheme is tested. CI runs Linux amd64. Development happens on macOS. Windows
  and arm64 are not run.

** Requirements

- Chez Scheme 10.4.1 or newer, the full system (not Petite: the ahead-of-time
  lane needs ~compile-program~)
- CMake 3.26 or newer

Discovery tries ~scheme~, ~chez~, ~chezscheme~ in that order. If it cannot find
a runtime, point it at one:

#+begin_src sh
cmake --preset dev -DURI_CHEZ_EXECUTABLE=/absolute/path/to/scheme
#+end_src

** Parsing a URI

~(uri collect)~ splits a URI into its five components and ~(uri components)~ reads
them. The core is bytevectors throughout, so a URI goes in as UTF-8 bytes and each
field comes back as bytes — or ~#f~ when the component is *absent*, which is never
confused with present-but-empty.

#+begin_src scheme
(import (rnrs)
        (uri collect)
        (uri components))

;; Parse a URI. The core works in bytevectors, so the input is UTF-8 bytes.
(define result
  (uri-parse 'uri (string->utf8 "https://example.com/path?q=1#top")))

;; Print one component, or "<absent>" when it never appeared (absent, not empty).
(define (show name bv)
  (display name) (display ": ")
  (display (if bv (utf8->string bv) "<absent>"))
  (newline))

(when (uri-parse-ok? result)
  (let ((c (uri-parse-components result)))
    (show "scheme"    (uri-components-scheme c))
    (show "authority" (uri-components-authority c))
    (show "path"      (uri-components-path c))
    (show "query"     (uri-components-query c))
    (show "fragment"  (uri-components-fragment c))))
#+end_src

Run it against the source libraries — ~src~ and the vendored ~byte-machine~:

#+begin_src sh
scheme --libdirs "src:vendor/byte-machine/src" --script parse.scm
#+end_src

#+begin_example
scheme: https
authority: example.com
path: /path
query: q=1
fragment: top
#+end_example

The mode is ~uri~ (an absolute URI); ~relative-ref~ and ~uri-reference~ are the
other two. Validating the component charsets and the host grammar is
~uri-parse-validate~ (parse and judge in one call), or ~uri-parse-result-validate~
to judge a result you already have — a reused collector's ~uri-collect-finish!~ —
without re-parsing. To judge one component's charset by itself, ~(uri charset)~'s
~validate-component~ takes the component's name, a bytevector, and an optional
~start~ and ~end~, and reports the first bad byte relative to ~start~. ~(uri host)~'s
~validate-authority~ does the same for an authority (~userinfo@host:port~), and
~authority-host-span~ gives the host's bounds within it, again relative to ~start~.
Parsing a bare
~host:port~ CONNECT target (RFC 9112 authority-form) is ~uri-parse-authority-form~.
Resolving a reference against a
base, normalizing, and recomposing live in ~(uri resolve)~, ~(uri normalize)~ and
~(uri recompose)~.

** The corpus

[[file:test/conformance/rfc3986/][test/conformance/rfc3986/]] is *derived*, not authored: extracted from
[[file:test/vendor/rfc3986.txt][the vendored RFC text]] by ~cmake/UriCorpus.cmake~, with the source's digest
recorded in ~PROVENANCE~. ~make corpus-refresh~ rewrites it and a registered
lane re-derives and compares, so a vector edited by hand reddens rather than
surviving. RFC 3986 §5.4 is the only normative vector set the RFC provides, and
all 42 of its rows must pass.
